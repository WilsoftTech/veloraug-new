**Differences from the plan:**

- **Local Postgres in place of a throwaway Neon branch.** The plan tests on a `migration-test` branch first. Instead, the automated tests set up a local Postgres 17.11 the way Neon is: the migration runs as an owner with `CREATEROLE` and `BYPASSRLS` that belongs to `neon_superuser`, not as a superuser, and a `neon_auth` schema exists. The migration runs in one transaction, and the checker leaves no data. A Neon throwaway branch is still possible, but it would need the owner string twice more.
- **The role password is generated by the script,** not typed by the owner. It goes straight into `.env` and is never shown. Running the script again replaces it.
- **The branch guard is new.** It was added after the incident below. The first version compared the database host's `ep-…` name with the one in the Auth URL. That was an unverified assumption. On the owner's first run it refused `ep-twilight-breeze-be9id8hj`, which was very likely the right branch. It was replaced by a check for Neon Auth's `neon_auth` schema. On the next run that check passed, but the database was in **us-east-2**, the old project from before the move, which also had Auth. So the first check had been right: the earlier mismatch was a different project. Both checks now apply. The host must equal `VELORAUG_NEON_AUTH_URL`'s host without `.neonauth`, and the database must hold `neon_auth` tables. The scripts connect, check both and print the result, and only then change anything.
- **Neon accepts only plain passwords** in `CREATE ROLE`. It refused the SCRAM hash at commit, so the owner's run changed nothing. The role script sends the password itself to Neon, over TLS, and a hash only to local databases. It checks the role's rights after the commit, when Neon has applied the change, and removes a new role again if they're wrong.

## An incident during this step

While testing the checker on the local database, I made a mistake: the command meant to give it the local address left that setting empty. The checker then read `services/api/.env` and **connected to a Neon database with the saved `VELORAUG_DATABASE_URL`**. I didn't see the connection string: the checker printed only the host, `ep-wild-wave-b9l7rt06.c-7.eu-central-1.aws.neon.tech`. It stopped at "profiles doesn't exist". Before that point it had run only reads, plus checks that stop it before any write could succeed. **Nothing on Neon was changed.**

Two things came out of it:

- **The saved database URL needed replacing.** It didn't use `veloraug_app`, and its endpoint, `ep-wild-wave-b9l7rt06`, isn't the sign-in branch's. It may be the Frankfurt default branch, which the plan keeps empty. The role script has since replaced this line.
- **Fixes.** The migration and both scripts refuse a Neon database that isn't the sign-in branch, as described above. The checker refuses any role other than `veloraug_app` before connecting, and every write it tries is rolled back, even if it succeeds. Rerun with the real `.env`, it refused before connecting. Tests no longer read the real `.env`.

## Before real users

- **The old us-east-2 project's owner password** was pasted into `services/api/.env` by hand during this step, before the role script replaced that line. Reset that password in the old project's Console, or delete the old project if nothing in it is needed.
